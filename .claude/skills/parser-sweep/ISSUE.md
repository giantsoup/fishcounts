# Parser bug issue format

One issue per group, filed with `gh issue create --label parser-bug --label ready-for-agent --title "<title>" --body-file <file>`. The repo is public. Quote at most a few lines of a report's paragraph, the smallest excerpt that shows the failure. Credentials, cookies, and anything else the API marked `[REDACTED]` stay out.

Write it for the implementer who picks it up cold, in the durable, behavioural style of `~/.claude/skills/triage/AGENT-BRIEF.md`. Describe parser behaviour and contracts, not file paths or line numbers.

**Title:** `<source>: <what the parser gets wrong>`, for example `seaforth_landing: half-day counts read as anglers when the trip line wraps`.

```markdown
> *This was generated by AI during a parser sweep.*

## What goes wrong

<one or two sentences in GLOSSARY.md terms: the parser error type, the source, and what the parser produced versus what the report says>

## Evidence

- Parser errors: #<id>, #<id> (source `<source>`, target dates <dates>)
- Raw payloads: <ids>
- Excerpt:

  > <minimal excerpt>

- Parser produced: <the relevant parsed fields from evaluate>
- Report says: <the correct reading>

## Recommended fix

<the parser behaviour to change, and why that is the root cause, not just this symptom. Name the parser and the rule or pattern involved.>

## Acceptance criteria

- [ ] A regression test parses a fixture built from raw payload <id>'s report text. It fails before the fix and passes after.
- [ ] The dry-run evaluate of payload <id> no longer raises `<error_type>`.
- [ ] Reports from the same source that already parse correctly are unchanged.
```
